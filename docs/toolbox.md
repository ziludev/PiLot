# Where the coding tools run

`bash`, `read`, `write` and `edit` execute in a separate Go process, `toolbox-go/`, not inside the
agent. The Node side keeps the tool schemas and a thin proxy, so the model sees the same names,
parameters, result shapes, truncation, exit codes and diagnostics it saw when the tools ran
in-process — that equality is what `tests/toolbox-parity.test.ts` and
`tests/toolbox-files-parity.test.ts` assert, by running pi-durable's own tools against a real
environment and comparing both paths field by field.

At boot the agent starts `toolbox-go/bin/toolbox` on a unix socket under `.data/` and installs the
proxies under the extension name `coding-tools`, which is where pi-durable's own tools lived, so
nothing downstream changes. The binary is rebuilt from source whenever any `toolbox-go/**/*.go`
file is newer than it, and `AGENT_TOOLBOX_BIN` moves it elsewhere.

There is no in-process implementation left and no fallback: a toolbox that cannot answer aborts the
boot, so a turn never runs half on Go and half on Node. A machine without a Go toolchain therefore
needs a prebuilt binary; a broken binary is a build problem, not a switch to flip.

## Unicode normalization

`read` path lookups and `edit`'s fuzzy matching need Unicode normalization, which Go's standard
library does not provide. `toolbox-go/internal/unicodenorm` therefore carries the tables as data,
generated by `internal/unicodenorm/generate.py` from the Unicode database Python ships with, and
implements NFD/NFKC on top of them.

The generator refuses to run when Python's Unicode version differs from the version node reports,
because a stale table changes what `edit` can match. Regenerate with:

```bash
cd toolbox-go && python3 internal/unicodenorm/generate.py > internal/unicodenorm/tables_gen.go && go test ./...
```

Its test checks idempotence and canonical ordering across every code point, and the parity suite
covers a ligature, full-width text, a character added after Unicode 13 and an NFD filename.
